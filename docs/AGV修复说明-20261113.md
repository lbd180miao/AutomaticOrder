# AGV PLC 与独立视觉触发修复

## 本次处理

- 设备健康页在监听运行时复用后台采样，避免每次刷新另开 S7 连接争用文件锁。Windows 文件锁短间隔重试，超时显示本地锁竞争原因。
- 视觉首次高电平受理一次；已保存电平跨重连保留，持续高电平不重复拍照。MES 封箱仍按上升沿和自身业务条件处理。
- 料框码、3D、泡棉、MES 封箱四路独立受理，无工序先后门槛。单路异常只写设备页面报警记录，不写工位锁定位、不创建解锁流程、不挡住其他路。
- NoRead 视为扫码失败标记，不送入料框 MES 查询。
- 3D 采集前创建视觉历史任务，采集/配置/计算失败保存错误；成功计算复用同一任务归档。
- 设备页第五部分“报警记录”可展开，逐条查看详情，只用一个年月日查询当天记录。沿用 48 小时记录窗口，最多显示最近 50 条。

## 原因与边界

现场截图出现 Errno 36（Windows 本地资源锁错误），旧版健康检查和采样争锁可导致读取状态抖动；仅凭截图无法排除现场网络问题。旧版把启动/重连时的 True 重新作为基线，因此可能没有派发拍照。NoRead 或某路失败又可能进入全局锁定，阻断其他视觉请求。

输入采样独立运行，业务按队列受理；共用 PLC 通信仍串行，长时间相机计算会让其他已采样业务排队，不丢掉采样到的变化。不承诺检测到短于采样周期的脉冲。

不更改算法发布许可：3D 算法未允许 PLC 发布时，记录错误而不强行写入有效补偿。MES 已提交但结果需核对时保留上下文，不盲目重复封箱。

## 验证

本次相关 Django 测试 94 项通过，部署角色 8 项、启动/打包入口 5 项通过。覆盖日期筛选、四路单路失败隔离、不锁工位、启动高电平、重连去重、NoRead、真实相机接口异常历史及同一任务归档。

最终 AGV EXE 已通过自动监听与四点页面冒烟验证，以及真实模式下无硬件、相机子进程异常退出/重启而网页持续可用的隔离验证。包内设备页模板与源码 SHA256 一致。

部署审计通过：18 个配方引用的标准模板，视觉历史表为空，无白名单之外的图像或点云；7 张配方/标定相关表逐行与源数据库一致，数据库完整性和外键检查通过。报告位于部署目录上一级 clean-release-audit.json。

扩展旧测试集发现旧握手测试仍假定软件复位输入、等待反馈复位和全局锁站，与现有四输入协议及本次独立监听要求不符；未将整个仓库测试集宣称为全部通过。

本地没有 PLC/相机，以上为软件回归及离线验证，不能替代现场真实拍照验收。

## 部署

完整复制 AGVControl 文件夹，不要只复制 EXE。AGV 自动监听，MES 只经 HTTP 发往外部电脑；外部电脑继续使用完整应用及 MES 网关。

升级前退出旧程序并备份现场数据。保留现场数据库、配方、标定、相机参数和网关配置；不要用开发数据库覆盖现场新增数据。程序目录自带数据库是构建时快照。

软件侧已取消四路业务错误的全局锁定门槛；现场旧 PLC 锁定位若曾置位，请由现场 PLC 工程师按设备状态确认恢复，软件不会在启动时盲目清除旧硬件输出。

验收时分别单独触发 3D、泡棉、料框和封箱；查看设备页监听记录及报警记录，检查视觉历史。持续高电平不应重复拍照；先低后高后可执行下一次。任一路失败后，其他路仍应受理。
